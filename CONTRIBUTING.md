# Contributing to Kapital Launcher

Kapital Launcher is a personal launcher for the Kapitel Kapital packs. It is
early software, so a bug report or an idea is worth as much as code.

## Reporting a bug or asking for a feature

Everything goes through **GitHub Issues**, which offers a short form: a bug
report, a feature request, or a question. You do not need to be technical to
file a good one. The forms ask for things you can see: what you were doing,
what you expected, which version and operating system. "Not sure" is a real
answer.

One thing to leave out: Prism's own files. `accounts.json` holds your Microsoft
session and never belongs in an issue.

Found a security vulnerability? Do not open an issue. See [SECURITY.md](SECURITY.md).

## What happens after you file

Every new issue arrives labelled `status:needs-triage`. Triage adds three
labels: what kind of change it is (`type:`), which part of the app it touches
(`area:`), and how urgent it is (`p0` to `p3`, from the form's own priority
question). Titles are kept to a short noun phrase with the area left to the
label, so an issue may be retitled. That is housekeeping, not a judgement.

## Contributing code

The project is GPL-3.0-only (`LICENSE`); a contribution is made under the
same licence.

Start from an issue. Setup and the dev loop are in the [README](README.md);
conventions and the full command list are in
[`agent_docs/CLAUDE.md`](agent_docs/CLAUDE.md). Run the gates before opening
a pull request:

```bash
.claude/suite-check.py
```

That is the same list CI runs.

### Pull requests

Merged pull requests become the release notes: each line of a pull request's
Changelog section, or the title of one without, so both are copy, not a note
to a reviewer.

- **Title:** imperative mood, sentence case, no trailing period, one line.
  Say what changed, not which files moved.
- **No em dashes** anywhere in the title or body. Use a comma, a colon, or
  two sentences. CI checks this (`pr-copy`).
- **List the changes** in the body's `## Changelog` section, one
  `- type: text` line each (`feature`, `fix`, `chore`, `docs` or `skip`). Each
  line is release-notes copy with the same rules as the title, and each lands
  on its own line under the section its type names. Which type is below.
- **Or label it** with one `type:` (`feature`, `bug`, `chore`, `docs`) when it
  is one change and has no section: the label files it, by its title.
- **Label it with an `area:`** either way. CI's `pr-labelled` status needs the
  area and one of the two above, and warns when it falls back to the title.
- **One pull request per piece of work.** A session's small fixes and tweaks
  are one pull request with a Changelog line each. Split only when a part is
  risky on its own, has to be revertable on its own, or ships at a different
  time.
- **Body:** why the change exists and how you verified it.

### Which type

The type, on a Changelog line or as the `type:` label, is the only input to
where a change lands in the release notes. Ask these in order and stop at the
first yes:

1. **Can a user of the launcher tell the difference?** If nothing they can
   see, run or click changed, it is `type:chore`, or `type:docs` when it is
   documentation and nothing else. Refactors, tests, CI, tooling and
   dependency bumps stop here, however large the diff.
2. **Was the launcher already meant to do this, and not doing it?** Then it
   is `type:bug`. That covers anything the UI offers or plainly implies.
3. **Otherwise it is `type:feature`:** the app can now do something it never
   offered.

The size of the diff is not the test, and the title's verb is not the test.
Imagine the change reverted: something goes back to being broken is a bug,
they lose something they never had is a feature, they cannot tell is a chore.

`changelog:skip` leaves a pull request out of the notes entirely. It silences a
Changelog section too, and does not replace one or a `type:` label.

### Commit messages

The same rules as titles: imperative, sentence case, no em dashes. Nothing
parses them, but they are read.

### Things not to edit by hand

- `frontend/wailsjs/`: Wails IPC bindings. `wails generate module`.
- `frontend/src/styles/tokens.css`, `tokens.ts`, `backend/design/design_gen.go`:
  generated by `pnpm gen:tokens` from `design/tokens.json`.
- `.github/workflows/pr-labelled.yml`, `aislop.yml`, `issue-priority.yml`,
  `.github/scripts/release-notes*.py`, `.github/release.yml`,
  `.aislop/base.yml`, `.claude/suite-*.py`: vendored from
  `kollektiv-mc/Kollektiv`. Change them there and copy the file.
- `.github/workflows/codeql.yml`, `scorecard.yml`: vendored from
  `kollektiv-mc/Konnekt`. Same rule.
- `frontend/pnpm-lock.yaml`, `pnpm-lock.yaml`: pnpm owns their layout.

CI checks all of these, so a hand edit shows up as a failing job.

## Code of conduct

Be decent to people. This is a small project with no formal process; if
someone is making it unpleasant, say so, and it will be dealt with.
